# Проверка repair на Linux / Raspberry Pi

Версия для проверки: 3.3.0. Постоянное имя скрипта — gnss-caster-install.sh. Успешный repair, поток от приёмника и выдача RTCM тестовому NTRIP-клиенту ранее проверены на Raspberry Pi для версии 3.0.12; это не проверка новой версии. Результаты локальных проверок — в `validation/audit/REPORT.md`. Сценарии намеренных ошибок на устройстве и RTK-решение реального ровера ещё не проверены.

После установки проверить оба языка кабинета и независимый язык Telegram: сохранение, повторный вход, русские кнопки и уведомления. Отправку пробного сообщения выполнять только при разрешённой проверке на устройстве.

## Перед запуском

- Сохранить закрытую резервную копию приложения, согласованную копию SQLite и настройки системы. Учитывать, что установленный backup.sh может отправлять архив в Telegram; при проверке 2026-09-09 создан отдельный локальный архив без вызова backup.sh.
- Записать текущие версии Python и приложения, активность и автозапуск caster, активность nginx и UFW.
- Убедиться, что в `/var/backups/gnss-caster` достаточно места для дополнительной копии приложения и всего окружения Python. Во время ремонта caster будет остановлен.

Команды для фиксации состояния:

```sh
python3 --version
systemctl is-active gnss-caster
systemctl is-enabled gnss-caster
systemctl is-active nginx
sudo ufw status
```

Последняя команда нужна только при установленном UFW.

## Успешный ремонт

Из каталога с новой копией установщика:

```sh
sudo bash ./gnss-caster-install.sh --repair
```

Проверить:

- В выводе есть путь созданного снимка и успешная финальная проверка.
- Версия приложения — 3.3.0, веб-интерфейс открывается и вход работает.
- При исходно активном caster снова доступны подключение приёмника и передача RTCM роверу.
- Автозапуск caster совпадает с исходным. Если перед ремонтом caster был остановлен, после временного запуска для проверки он снова остановлен.
- Активность nginx сохранена. При активном UFW действуют ожидаемые правила портов.
- Секрет загружается из `/etc/gnss-caster/secrets/secret.env`; содержимое не выводить в диагностические журналы.

## Ошибки и прерывания

Сценарии намеренной поломки проверять на отдельной тестовой установке или клоне накопителя:

- Неудачная установка зависимостей.
- Ошибка замены модуля или шаблона.
- Прерывание TERM в середине ремонта.
- Неудачная финальная проверка здоровья.
- Повреждение снимка или ошибка его копирования при откате.
- Ошибка перезагрузки UFW.

При штатном откате должны восстановиться приложение, окружение Python, база, сохранённые конфигурационные файлы и исходное состояние служб. Исходный код ошибки должен остаться ненулевым. При неполном восстановлении не должно быть сообщения об успешном откате; снимок должен сохраниться для разбора.

## Ограничения

Журналы и диагностические копии сохраняются. Изменения системных пользователей/групп и прав общих каталогов не откатываются. SIGKILL и отключение питания не обрабатываются ловушками Bash; для этих случаев нужна отдельная процедура ручного восстановления. Текущие локальные тесты подменяют systemd и UFW, поэтому не заменяют описанную проверку на Linux.

## Обновление через веб: отдельный стенд

Перед публикацией стабильного выпуска проверить на клоне установки без полевой работы:

- Отказ для viewer/operator, отсутствие CSRF, неверный пароль и предел попыток. Проверить отсутствие пароля в журнале аудита.
- Проверку стабильного выпуска, отсутствие выпусков, недоступный GitHub, неверные часы, HTTP 403/429, повреждённый файл и изменившийся после выбора digest. До проверки целостности установщик не должен исполняться.
- Отказ при активном ровере, другом обслуживании и нехватке диска. Повторный запрос не должен создавать вторую задачу.
- Успешный переход между двумя тестовыми версиями со снимком и сохранением настроек/пользователей. Для испытания updater использовать изолированную тестовую инфраструктуру; не подменять публичные стабильные файлы ради теста.
- Закрыть браузер во время обновления и открыть снова: состояние берётся с сервера. Перезапуск caster не должен убивать задачу установки.
- Намеренно сорвать установку и проверку здоровья: либо подтверждённый откат с доступным входом/БД/NTRIP, либо явная ошибка с сохранённым снимком. Проверить старый updater после отката.
- На одноразовом клоне прервать питание: после загрузки не должно быть ложного успеха. Восстановить систему из снимка/внешней копии и записать точную процедуру восстановления. Это условие допуска к эксплуатационному обновлению, а не тест на рабочем накопителе.

После стенда выполнить 48–72 часа наблюдения с реальным приёмником и ровером по отдельно разрешённому плану. Сохранять эксплуатационные журналы вне публичного репозитория.
