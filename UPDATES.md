# Обновление GNSS Caster через веб

Функция доступна начиная с 3.3.0. Старую установленную версию сначала нужно один раз обновить вручную новым `gnss-caster-install.sh --repair` в согласованное окно обслуживания. Публикация кода в GitHub сама по себе станцию не обновляет.

## Для администратора станции

1. Завершить полевые работы, сохранить независимую резервную копию и отключить роверы.
2. Открыть **System settings → Updates** / **Системные настройки → Обновления**.
3. Нажать **Check for updates** / **Проверить обновления**. Нужен доступ устройства к GitHub по HTTPS и корректное системное время.
4. Прочитать описание выпуска, нажать установку новой версии. Ввести текущий пароль администратора и `UPDATE`.
5. Дождаться результата. Передача поправок и веб временно прерываются; запрос установки повторять не следует. Обновление продолжает отдельная служба systemd, состояние сохраняется на диске.
6. После успеха перезагрузить страницу, проверить диагностику, свежесть RTCM и фактическое получение поправок ровером.

Доступны только более новые опубликованные стабильные выпуски из `stepm65/GNSS-Caster`; draft, prerelease и ветки не устанавливаются. Отсутствие нового выпуска — нормальное состояние. Проверка запускается вручную; опрос состояния не обращается в GitHub. При ограничении GitHub API нужно повторить проверку позже.

Сейчас поддерживается стандартный путь БД `/opt/gnss-caster/instance/db.sqlite`. Активный ровер, включённый режим полевых работ, другая операция обслуживания, недостаток диска, устаревший выбор выпуска или несовпадение SHA-256 блокируют установку.

С версии 3.3.2 приём нового ровера и начало обслуживания используют общую блокировку. После её захвата помощник повторно читает счётчики и режим полевых работ; новые клиенты временно получают 503. Блокировка удерживается до завершения установки, восстановления или отката. Она также применяется к repair и отложенным запросам перезапуска/перезагрузки. Создание копий остаётся доступным при подключённых роверах.

Перед сменой включите **System settings → General → Field work in progress — block maintenance** (в русском интерфейсе: «Полевые работы — запретить обслуживание»). Режим запрещает перечисленные операции даже при временном отключении всех роверов. После смены администратор отключает его и убеждается, что роверы завершили работу. Это защита операций приложения, а не запрет прямых команд root или отключения питания. Первый переход с более старой версии требует окна без полевых работ: старый NTRIP-сервер ещё не знает об общей блокировке.

## При неудаче

Установщик использует транзакцию `--repair`: остановка caster, снимок приложения/окружения/БД/конфигурации, установка, проверка здоровья, восстановление прежнего состояния служб. При штатной ошибке пытается откатиться. Веб сообщает **«предыдущая версия восстановлена»** только при явном подтверждении установщика. Это не проверка Bluetooth или точности RTK.

При отключении питания или принудительном завершении откат не гарантирован. Если веб недоступен, администратор проверяет через SSH:

```sh
sudo systemctl status gnss-caster-release-update.service --no-pager
sudo journalctl -u gnss-caster-release-update.service -n 100 --no-pager
sudo tail -n 100 /var/lib/gnss-caster-updates/maintenance.log
sudo cat /var/lib/gnss-caster-updates/state.json
```

Файл состояния содержит результат и, если установщик его сообщил, путь снимка. После перезагрузки незавершённая операция отмечается как прерванная. Снимки в `/var/backups/gnss-caster` не удаляются автоматически; их состав и свободное место нужно контролировать. Если программа не запускается, восстановление выполняют по проверенному сценарию со снимком, а не повторными нажатиями установки. Журнал может содержать эксплуатационные сведения — не публиковать его без просмотра.

## Остановка и сроки обновления

Начиная с 3.3.1, надзор за установщиком передаёт запрос остановки его группе процессов и ждёт откат. Для снимка, зависимостей, настройки, миграции и проверки здоровья действуют отдельные сроки (10, 30, 15, 10 и 5 минут), общий срок установки — 60 минут. Для завершения отката отведено до 15 минут; принудительное завершение после этого помечается как прерывание, а не успешное восстановление. Эти пределы не являются оценкой обычной длительности обновления.

Путь снимка и этап сохраняются во время работы, состояние обновляется примерно каждые пять секунд. Потеря питания по-прежнему требует отдельного сценария восстановления; надзор за процессом не заменяет его.

## Для выпуска новой версии

1. Изменить версию установщика и `frontend/package.json`, обновить `CHANGES.md`, собрать/встроить фронтенд. При изменении updater выполнить `python tools/embed_release_updater.py`.
2. Пройти PR и CI, затем открыть GitHub Actions → **Prepare stable release**, выбрать `main` и версию `X.Y.Z`, совпадающую с установщиком.
3. Workflow повторно выполняет проверки и создаёт **черновик** `vX.Y.Z` с проверенным `gnss-caster-install.sh`, `SHA256SUMS` и описанием из журнала изменений. Публикация не автоматическая.
4. После проверки кандидата на отдельном Linux-стенде опубликовать выпуск как стабильный. GitHub должен вернуть для файла `digest: sha256:…`; без него updater откажет. Не заменять файл уже опубликованного выпуска — исправления выпускать под новой версией.

Root-helper доверяет фиксированному репозиторию и HTTPS GitHub, не импортирует приложение или его конфигурацию как Python-код, хранит файлы в закрытом каталоге root и запускает только проверенный установщик. SHA-256 из того же GitHub не является независимой цифровой подписью. Защита аккаунта владельца и процесса публикации обязательна для этой модели доверия.
