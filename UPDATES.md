# Обновление GNSS Caster через веб

Функция доступна начиная с 3.3.0. Старую установленную версию сначала нужно один раз обновить вручную новым `gnss-caster-install.sh --repair` в согласованное окно обслуживания. Публикация кода в GitHub сама по себе станцию не обновляет.

## Для администратора станции

1. Завершить полевые работы, сохранить независимую резервную копию и отключить роверы.
2. Открыть **System settings → Updates** / **Системные настройки → Обновления**.
3. Нажать **Check for updates** / **Проверить обновления**. Нужен доступ устройства к GitHub по HTTPS и корректное системное время.
4. Прочитать описание выпуска, нажать установку новой версии. Ввести текущий пароль администратора и `UPDATE`.
5. Дождаться результата. Передача поправок и веб временно прерываются; запрос установки повторять не следует. Обновление продолжает отдельная служба systemd, состояние сохраняется на диске.
6. После успеха перезагрузить страницу, проверить диагностику, свежесть RTCM и фактическое получение поправок ровером.

Доступны только более новые опубликованные стабильные выпуски из `stepm65/GNSS-Caster`; draft, prerelease и ветки не устанавливаются. Отсутствие нового выпуска — нормальное состояние. Проверка запускается вручную; опрос состояния не обращается в GitHub. При ограничении GitHub API нужно повторить проверку позже.

Сейчас поддерживается стандартный путь БД `/opt/gnss-caster/instance/db.sqlite`. Активный ровер, включённый режим полевых работ, другая операция обслуживания, недостаток диска, устаревший выбор выпуска или несовпадение SHA-256 блокируют установку.

С версии 3.3.2 приём нового ровера и начало обслуживания используют общую блокировку. После её захвата помощник повторно читает счётчики и режим полевых работ; новые клиенты временно получают 503. Блокировка удерживается до завершения установки, восстановления или отката. Она также применяется к repair и отложенным запросам перезапуска/перезагрузки. Создание копий остаётся доступным при подключённых роверах.

Перед сменой включите **System settings → General → Field work in progress — block maintenance** (в русском интерфейсе: «Полевые работы — запретить обслуживание»). Режим запрещает перечисленные операции даже при временном отключении всех роверов. После смены администратор отключает его и убеждается, что роверы завершили работу. Это защита операций приложения, а не запрет прямых команд root или отключения питания. Первый переход с более старой версии требует окна без полевых работ: старый NTRIP-сервер ещё не знает об общей блокировке.

## При неудаче

Установщик использует транзакцию `--repair`: остановка caster, снимок приложения/окружения/БД/конфигурации, установка, проверка здоровья, восстановление прежнего состояния служб. При штатной ошибке пытается откатиться. Веб сообщает **«предыдущая версия восстановлена»** только при явном подтверждении установщика. Это не проверка Bluetooth или точности RTK.

При отключении питания или принудительном завершении откат не гарантирован. Если веб недоступен, администратор проверяет через SSH:

```sh
sudo systemctl status gnss-caster-release-update.service --no-pager
sudo journalctl -u gnss-caster-release-update.service -n 100 --no-pager
sudo tail -n 100 /var/lib/gnss-caster-updates/maintenance.log
sudo cat /var/lib/gnss-caster-updates/state.json
```

Файл состояния содержит результат и, если установщик его сообщил, путь снимка. После перезагрузки незавершённая операция отмечается как прерванная. Снимки в `/var/backups/gnss-caster` не удаляются автоматически; их состав и свободное место нужно контролировать. Журнал может содержать эксплуатационные сведения — не публиковать его без просмотра.

## Локальное восстановление с версии 3.3.3

До остановки caster установщик сохраняет журнал и программу возврата в закрытом каталоге снимка. Готовность снимка фиксируется после сохранения файлов, каталогов и их хешей на диске. Программа управления журналом находится отдельно от приложения и его Python-окружения, поэтому повреждённый веб не мешает её запуску:

```sh
sudo python3 -I /var/lib/gnss-caster-maintenance/recovery.py status
```

Найдите незавершённую операцию: идентификатор, предыдущую версию, этап, признак готовности снимка и исходное состояние служб. В выводе есть готовая команда `recover <идентификатор> --confirm`. Выполняйте её после завершения полевых работ. Она проверяет содержимое до изменения службы и возвращает исходные файлы и состояние активности; ранее выключенная служба останется выключенной. Для работающей службы проверяются роверы и режим полевых работ. Для уже остановленной службы явное локальное восстановление допускается и при повреждённой БД.

Если создание снимка не завершилось, изменения программы ещё не начинались: команда восстанавливает только прежнее состояние служб. Если снимок был готов, возвращаются его файлы и БД. Повреждённый снимок отклоняется; при неудаче результат остаётся незавершённым, снимок сохраняется, повтор команды допускается после устранения причины. Снимки завершённых операций этой командой не откатываются.

Перед каждым запуском службы проверяется журнал. Незавершённая операция после перезагрузки или потери процесса блокирует запуск до восстановления. Во время штатного обслуживания запуск для проверки здоровья разрешён при подтверждённых процессе, загрузке ОС и удерживаемой блокировке. Это отдельная фиксированная root-команда перед запуском; основной веб-процесс сохраняет своего непривилегированного пользователя ([документация systemd](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#ExecStart=)).

Первый переход со старой версии ещё не имеет такой проверки в старом systemd-unit до его замены. Поэтому первый переход требует отдельного окна и проверенного пути возврата. Старые снимки без `transaction.json` не рассматриваются как новые проверенные операции. Журнал защищает от известных прерываний процесса; он не гарантирует восстановление после физического повреждения накопителя.

## Остановка и сроки обновления

Начиная с 3.3.1, надзор за установщиком передаёт запрос остановки его группе процессов и ждёт откат. Для снимка, зависимостей, настройки, миграции и проверки здоровья действуют отдельные сроки (10, 30, 15, 10 и 5 минут), общий срок установки — 60 минут. Для завершения отката отведено до 15 минут; принудительное завершение после этого помечается как прерывание, а не успешное восстановление. Эти пределы не являются оценкой обычной длительности обновления.

Путь снимка и этап сохраняются во время работы, состояние обновляется примерно каждые пять секунд. После потери питания используйте локальное восстановление, описанное выше; надзор за процессом сам по себе не возвращает файлы после отключения ОС.

## Обновление по SSH одной командой

Тот же выпуск можно установить без веба, от root:

```sh
sudo bash -c 'bash <(curl -Ls https://raw.githubusercontent.com/stepm65/GNSS-Caster/main/install.sh)'
```

`install.sh` берёт последний опубликованный стабильный выпуск (или указанный тег `vX.Y.Z`), проверяет `gnss-caster-install.sh` по `SHA256SUMS` того же выпуска и по версии в теге, затем запускает `--repair` на установленной системе или `install` на новой. Более новая установленная версия не заменяется без `--allow-downgrade`. Режим установщика можно задать явно после `--`, например `-- --status`. Вариант `dev-latest` берёт установщик из `main` без проверки суммы и годится только для тестового стенда. Если опубликованных выпусков нет, команда завершается с сообщением и ничего не устанавливает.

Подготовка перед обновлением та же, что и для веба: завершить полевые работы, сделать резервную копию, отключить роверы.

## Выпуск новой версии

Выпуски публикуются из Git-тегов `vX.Y.Z`, как в `amneziawg31-installer`.

1. В PR изменить `CASTER_VERSION` в установщике и `version` в `frontend/package.json`, добавить в `CHANGES.md` раздел `## X.Y.Z …`, собрать/встроить фронтенд и выполнить нужные `tools/embed_*.py`. Слить PR в `main` после CI.
2. Проверить кандидат на отдельном Linux-стенде: `bash <(curl -Ls …/install.sh) dev-latest` или установщик из клона.
3. Создать и отправить тег на слитом коммите:

   ```sh
   git switch main && git pull
   git tag v3.5.0
   git push origin v3.5.0
   ```

   Либо на github.com: **Releases → Draft a new release → новый тег `v3.5.0` на `main` → Publish**.
4. Workflow **Release** проверяет формат тега, что коммит находится в `main`, совпадение версии в установщике, `package.json` и `CHANGES.md`, повторно запускает все проверки, собирает `SHA256SUMS` и описание из журнала изменений и **публикует** выпуск `GNSS Caster X.Y.Z` с `gnss-caster-install.sh` и `SHA256SUMS`. После этого выпуск сразу виден веб-обновлению и `install.sh`.
5. При ошибке проверки выпуск не публикуется. Исправить в `main`, удалить неудачный тег (`git push --delete origin v3.5.0; git tag -d v3.5.0`) и выпустить заново; если выпуск уже опубликован — только новой версией.

Файлы опубликованного выпуска не заменяются: повторный запуск для того же коммита ничего не меняет, а другой файл под той же версией отклоняется. Выпуск, созданный на github.com, получает файлы через минуту-две после публикации; в это время веб-проверка может сообщить об отсутствии установщика — повторите позже. Отправка тега этого окна не создаёт.

Публикация по тегу автоматическая, поэтому защитите `main` и теги в настройках репозитория (Rulesets: запрет force-push и удаления, обязательный CI; при возможности — ограничение создания тегов `v*` владельцем) и аккаунт владельца (2FA).

Root-helper доверяет фиксированному репозиторию и HTTPS GitHub, не импортирует приложение или его конфигурацию как Python-код, хранит файлы в закрытом каталоге root и запускает только проверенный установщик. SHA-256 из того же GitHub не является независимой цифровой подписью. Защита аккаунта владельца и процесса публикации обязательна для этой модели доверия.
